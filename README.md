# match-viewer-prototype

A 2D football match viewer that replays a full match from minute 0 to 90,
continuously and accelerated, from an **event log** (one pitch position per
event, nothing per tick). PixiJS 8 + TypeScript, no framework, no backend.

Open `dist/match_viewer_demo.html` in a browser and it runs. Drop your own
JSON log onto the page to replay it instead of the sample match.

Built as a working prototype, not a client project: the sample match is
synthetic, generated by `tools/gen_log.ts` to exercise the parts that decide
whether a replay engine works — interpolation, reading order, camera, a clock
that never stops.

## What it does

- Running clock, scoreboard, possession marker, event feed, radar of all 22.
- Camera follows the ball with lookahead, creeps in near either box, zooms
  and shakes on goals, pulls back for half-time.
- Speed 1× to 120×. **Key moments stay readable at any speed**: a goal plays
  at about 2.5× real time whether the replay runs at 10× or 120×, then the
  rate eases back up. No cut, no freeze; the clock keeps running.
- Seek anywhere by clicking or dragging the timeline; the result is exact.
- Half-time change of ends, cards shown over the player's head, red cards
  walk off, scorer celebrates, confetti.
- Cartoon players with a run cycle, facing direction, kits and numbers from
  the log's team metadata.

## How it works

**State is a pure function of the log and the clock.**
`stateAt(index, T)` in `src/engine.ts` computes every player position, the
ball (with height), the score, the possession, the key moment and the feed
from the log and `T` alone. Nothing is accumulated between frames. Two
consequences: seeking is exact rather than approximate, and the same log
always produces the same replay. `npm test` checks exactly that by sampling
the match in a shuffled order and comparing against playback order.

**Moving a player between two events.** Each event is a keyframe for the
player it names. Two events close together (≤30 s): the player walks the
real line between them with an ease in and out, arriving on the logged
timestamp. Long gap: holding a straight line for forty seconds looks dead, so
the player returns to a formation anchor after the first event and leaves it
just in time to reach the second. A player carrying the ball runs with it.
The log stays authoritative; no path is invented that the log does not
support.

**Keeping the other twenty plausible.** They are driven by shape, not by
events. Each has an anchor in the team's formation (4-3-3 and 4-4-2 in the
sample), the whole block slides along the pitch and leans toward the ball's
side, and compresses or spreads with the phase of play. The block follows a
*smoothed* ball position (a short triangular kernel over the last seconds),
so a 20 m/s pass does not drag twenty players with it. A small deterministic
drift keyed to shirt number keeps them breathing without ever becoming random.

**Ball between events.** A kick flies from the event position to the next
event position with a type-dependent speed and arc (a cross goes higher than
a pass; a clearance higher still); a carry moves with the runner; a dead ball
sits, then gets moved to the restart spot. Height is drawn as lift plus a
shrinking shadow, and fast flight leaves a short streak.

**Playback rate is a pure function too.** `rateAt(index, T, speed)` returns
the multiplier to apply this frame. Near a goal it holds the effective speed
at ~2.5× real time for six match seconds and eases back over six more; cards,
saves and half-time have their own profiles. Because it depends only on the
clock, offline capture with a fixed timestep produces the same footage as
live playback.

**The renderer never touches the state.** `src/render/` reads a `MatchState`
and draws it. Swapping PixiJS for another drawing layer, or adding a
per-tick position stream that overrides the keyframes, changes nothing in
the engine.

## Log format

```ts
interface MatchEvent {
  t: number;             // match seconds, monotonic
  type: 'pass' | 'carry' | 'cross' | 'shot' | 'save' | 'goal' | 'tackle' |
        'interception' | 'clearance' | 'foul' | 'freekick' | 'corner' |
        'throwin' | 'goalkick' | 'out' | 'kickoff' | 'halftime' | 'fulltime';
  team: 'home' | 'away';
  player: number;        // shirt 1..11, 0 = none
  x: number; y: number;  // metres, origin top-left; home attacks +x in the 1st half
  to?: number;           // receiver, for pass / cross
  outcome?: 'complete' | 'intercepted' | 'out' | 'saved' | 'goal' | 'wide' | 'blocked';
  card?: 'yellow' | 'red';
  score?: { home: number; away: number };
  period?: 1 | 2;
}
```

Full schema in `src/types.ts`. The sample log has ~1600 events, about one
every 3.4 seconds, which is the density of a real event feed.

## Files

| path | what it is |
|---|---|
| `src/engine.ts` | `buildIndex`, `stateAt`, `rateAt`, `cameraAt` — the whole model |
| `src/formations.ts` | formation anchors and the ball-relative shape logic |
| `src/render/` | PixiJS renderer: pitch, players, ball, HUD |
| `src/app.ts` | playback loop, controls, JSON loading, capture hooks |
| `tools/gen_log.ts` | deterministic synthetic match generator |
| `tools/build.mjs` | esbuild bundle → single self-contained HTML |
| `tools/record.mjs`, `tools/shot.mjs` | offline, fixed-timestep capture (video / stills) |
| `test/determinism.test.ts` | purity, speed sanity, ball bounds |
| `data/match_log.json` | the sample match |
| `dist/match_viewer_demo.html` | the build, everything inlined |

```
npm install
npm run gen        # regenerate the sample log (optional: node tools/gen_log.ts <seed>)
npm run typecheck
npm test
npm run build      # -> dist/match_viewer_demo.html
```

## Not done

Players are front-facing cartoons with a simple procedural run cycle, not
rigged characters; there is no sprite art, everything is drawn with Graphics.
No substitutions, no injuries, no referee. The camera is a smoothed follow,
not a directed broadcast.
